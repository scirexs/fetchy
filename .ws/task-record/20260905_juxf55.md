## Goal

Make a generic network error — the `TypeError` that `fetch` throws on a connection/DNS/TLS
failure — retryable, so a transient network blip can recover instead of surfacing on the
first attempt. Gate it behind a new retry option `retryOnNetwork` that mirrors the
existing `retryOnTimeout`, **defaulting to `true`**.

## Done when

- A network `TypeError` thrown from the fetch call is retried (with the same backoff as a
  status-code retry) up to `maxAttempts`, by default.
- Setting `retry: { retryOnNetwork: false }` restores the current single-attempt
  behavior for network errors.
- A user abort (`AbortError`) and any non-`TypeError` thrown value are **not** retried by
  this option; `TimeoutError` continues to be governed solely by `retryOnTimeout`.
- The new option is documented in `README.md` and recorded in ADR `002`.
- `deno check src/mod.ts`, `deno lint`, `deno fmt --check`, and `deno test` all pass.

## Background / constraints

`_shouldRetry(count, options, r)` decides retries. For a thrown value `r` (the `else`
branch), it currently retries **only** `TimeoutError` when `options.onTimeout` is set;
everything else returns `false`. `fetch` rejects with a `TypeError` on a network error and
with a `DOMException` (`TimeoutError` / `AbortError`) on timeout / abort, so `instanceof
TypeError` cleanly identifies a network error while excluding both timeout and user abort.

What must keep working:
- `TimeoutError` retry stays owned by `retryOnTimeout` / `onTimeout` — unchanged semantics,
  including no wait when `onTimeout` is `false`.
- `AbortError` (user cancel) and non-`TypeError` errors are never retried by the new flag.
- All shared retry gates still apply to network-error retry: `noIdempotent` (idempotentOnly),
  `maxAttempts`, and the backoff / `maxInterval` cap. Network-error retry does **not** consult
  `respectHeaders` (there is no response) — it waits via `_waitInterval(count, options)` with
  no headers, exactly like the timeout branch.
- Per ADR 001, the flag MUST NOT gate on `native`.

## Detailed changes

### (C-1) Internal option plumbing — `src/main.ts`

**Where:** `_DEFAULT`, `interface Options`, `type InternalRetry`, `_getRetryOption`.

**Required behavior:**
- `_DEFAULT` MUST gain `onNetwork: true`.
- `Options` MUST gain `onNetwork: boolean`.
- `InternalRetry` (the `Pick<Options, …>`) MUST include `"onNetwork"`.
- `_getRetryOption` MUST map the public flag: `onNetwork: options?.retryOnNetwork ?? _DEFAULT.onNetwork`.
  The existing `options === false` early return (`{ ..._DEFAULT, maxAttempts: 1 }`) needs no
  change — it already carries the default and forces a single attempt.

**Suggested implementation** (mirror `onTimeout` placement):
```ts
// _DEFAULT
onTimeout: true,
onNetwork: true,
// InternalRetry Pick union — add "onNetwork"
// _getRetryOption return object
onTimeout: options?.retryOnTimeout ?? _DEFAULT.onTimeout,
onNetwork: options?.retryOnNetwork ?? _DEFAULT.onNetwork,
```

### (C-2) Retry network TypeError — `src/main.ts` `_shouldRetry`

**Where:** the `else` (thrown value) branch of `_shouldRetry`.

**Required behavior:** a thrown value MUST be retried when it `instanceof TypeError` and
`options.onNetwork` is `true` (subject to the top-of-function `noIdempotent` /
`maxAttempts` gate already present), waiting via `_waitInterval(count, options)`. A
`TimeoutError` MUST keep its current `onTimeout`-gated behavior. Any other thrown value
(including `AbortError` and a plain `Error`) MUST return `false` with no wait.

**Suggested implementation:**
```ts
} else {
  if (r instanceof Error && r.name === "TimeoutError") return options.onTimeout && await _waitInterval(count, options);
  if (r instanceof TypeError) return options.onNetwork && await _waitInterval(count, options);
  return false;
}
```
**Note:** `&&` short-circuits so `_waitInterval` (and its delay) is skipped when the flag is
`false`, matching today's timeout behavior. `TimeoutError`/`AbortError` are `DOMException`s,
not `TypeError`, so the two `if`s are mutually exclusive and order-independent.

### (C-3) Public option — `src/types.ts` `RetryOptions`

**Where:** immediately after the `retryOnTimeout` member.

**Required behavior:** add `retryOnNetwork?: boolean` with a full `/** … @default true */`
doc comment (coding-style §10).

**Suggested implementation:**
```ts
/**
 * Whether to retry on a generic network error (the `TypeError` thrown by `fetch` on a
 * connection/DNS/TLS failure). User aborts and timeouts are not affected by this option.
 * @default true
 */
retryOnNetwork?: boolean;
```

### (C-4) README — `README.md`

**Where:** the `interface RetryOptions { … }` doc block and the `#### Default Values` block.

**Required behavior:** add a `retryOnNetwork` line to both, consistent with the existing

**Suggested implementation:**

### (C-5) ADR — create `.ws/decision/002-retry-network-errors.md`

Create the file with **exactly** this body:

```md
# 002. Retry generic network errors by default

**Status:** Accepted
**Supersedes:** none
**Date:** 2026-09-05
**Affects:** public option `RetryOptions.retryOnNetwork`; internal `Options.onNetwork`, `_DEFAULT`, `_getRetryOption`, `_shouldRetry`

## Context

`fetch` rejects with a `TypeError` on a network error (DNS failure, connection refused, TLS
failure, etc.) and with a `DOMException` (`TimeoutError` / `AbortError`) on timeout / abort.
Before this change, `_shouldRetry` retried only `TimeoutError` (gated by `retryOnTimeout`)
among thrown values; every other thrown error — including transient network `TypeError`s —
was surfaced on the first attempt with no retry, and callers had no way to opt into retrying
them.

Two forces shaped the choice: (1) how to identify a "network error" reliably without
catching a deliberate user abort or a deterministic programming mistake, and (2) whether
retrying such errors should be the default or opt-in.

## Decision

Add a retry option `retryOnNetwork` (internal `onNetwork`), defaulting to **true**,
mirroring `retryOnTimeout`. A thrown value is treated as a retryable network error iff
`value instanceof TypeError`. When enabled and the attempt / idempotency budget allows, such
errors retry with the same exponential backoff as status-code retries.

Detection is `instanceof TypeError` precisely because the fetch spec throws `TypeError` for
network errors while timeout / abort throw `DOMException`; `AbortError` (a deliberate user
cancel) and `TimeoutError` (owned by `retryOnTimeout`) are therefore excluded and never
retried under this flag.

## Consequences

- Behavior change: a network `TypeError` now issues up to `maxAttempts` requests by default
  where it previously issued one. Callers who want the old single-attempt behavior set
  `retry: { retryOnNetwork: false }` (or `retry: false`).
- Network-error retry obeys the shared gates: `maxAttempts`, `idempotentOnly`, and the
  backoff / `maxInterval` cap. It does not consult `respectHeaders` — there is no response.
- Consistent with ADR 001: the flag does not gate on `native`; retry semantics stay
  identical across modes.
- A custom `fetcher` that signals a network failure with a non-`TypeError` will not be
  retried under this flag; it must throw a `TypeError` to opt in.

## Rejected alternatives

- **Default false (opt-in).** Rejected: transient network errors are the paradigm case for
  retry, and `retryOnTimeout` already defaults to `true`; making the sibling opt-in would be
  inconsistent and leave the common case unprotected.
- **Retry any thrown `Error` except `AbortError` / `TimeoutError`.** Rejected: it requires
  explicitly excluding `AbortError`, and risks retrying deterministic programming errors
  (bad init, invalid header) that will only fail again. `instanceof TypeError` matches the
  spec and is precise.
- **A separate top-level `FetchyOptions` flag instead of a `RetryOptions` member.** Rejected:
  it is a retry concern and belongs beside `retryOnTimeout`, merged with the one-level `retry`
  precedence.
```

## Invariants / expected behavior

- `retryOnTimeout` behavior is byte-for-byte unchanged.
- Merge precedence (`setFetchy` ← `fy` ← per-call, `retry` merged one level deep) applies to
  `retryOnNetwork` automatically via `_buildOption` — no change needed there.
- `retry: false` ⇒ `maxAttempts: 1` ⇒ no network-error retry regardless of the flag.

## Out of scope

- Do not change status-code retry, `respectHeaders`, jitter, or timeout logic.
- Do not add any new top-level `FetchyOptions` field; the option lives only in `RetryOptions`.
- Do not touch `src/mod.ts` (no export changes) or `build_npm.ts` (no public runtime name added).
- No interceptor/middleware layer; no runtime feature detection.

## Accepted risks / tradeoffs

- Default `true` is a behavior change for existing callers relying on network errors failing
  fast; this is deliberate and documented (ADR 002, README). Opt out with
  `retry: { retryOnNetwork: false }`.
- A custom `fetcher` throwing a non-`TypeError` network signal is not retried — accepted;
  `TypeError` is the fetch-spec contract.

## Tests — `tests/main.test.ts`

Keep each block in `main.ts` declaration order and use the existing `makeOptions` helper
(it spreads `_DEFAULT`, so it already carries `onNetwork` once C-1 lands).

- `_DEFAULT` block: assert `_DEFAULT.onNetwork === true`.
- `_getRetryOption` block: assert the default (`_getRetryOption({}).onNetwork === true`)
  and the override (`_getRetryOption({}, { retryOnNetwork: false }).onNetwork === false`).
- `_shouldRetry` block:
  - returns `true` for a `TypeError` when `onNetwork` is `true` (use tiny `interval`).
  - returns `false` for a `TypeError` when `onNetwork` is `false`.
  - a non-`TypeError` `Error` still returns `false` (the existing "non-timeout errors" step
    already covers a plain `Error`; keep it).
  - an `AbortError` (an `Error`/`DOMException` with `name === "AbortError"`) returns `false`.
- `_fetchWithRetry` block: update/replace the current
  **"throws on network error (no retry by default)"** step — its premise no longer holds for a
  `TypeError`. Add a step where `fetch` rejects with a `TypeError` and assert it retries
  (`assertSpyCalls(mockFetch, maxAttempts)` then rejects) by default, and a step with
  `retry`/`onNetwork` disabled asserting a single call. A plain-`Error` rejection may
  remain as the "not retried" case.
